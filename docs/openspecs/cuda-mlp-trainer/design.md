# Design: GPU MLP training and independent reference parity

Read [proposal.md](proposal.md) for scope and authorization, [review.md](review.md) for the independent review and [tasks.md](tasks.md) for execution progress. This is the reviewed/authorized #11 contract, extending accepted [ADR 0003](../../adr/0003-replicated-sgd-training-contract.md) through [Accepted ADR 0005](../../adr/0005-cuda-training-reference-contract.md). The blocking tensor boundary remains [ADR 0004](../../adr/0004-blocking-host-staged-cuda-adapter.md).

## Approach and boundaries

Reuse `meshtrain.training` preparation, immutable inputs, worker supervision and numerical comparison. Add explicit `--device cpu|cuda:N` to `prepare` and `run`; default `cpu` preserves existing command behavior. CUDA preparation defaults to pinned staging, with `--host-memory pinned|pageable` available only for CUDA. A worker obtains its device/mode from the prepared config; it cannot override the group's workload after startup. Independent worker commands continue to take rank/config/output and explicit TCP endpoints.

The first supported CUDA placement is Linux/WSL x86-64, the locked CPython 3.12/Torch `2.14.1+cu132`/NumPy `2.5.4` runtime, and one logical indexed device shared by tiny worker processes. Every process resolves that index against its own visibility and records its actual UUID. Do not implement per-rank device placement or multi-device claims here. CUDA mode must use the strict index validation already established by #10, including rejection before Torch can wrap a large ordinal. Extract/reuse that validation internally if useful, preserving #10 behavior.

Components have separate responsibilities:

| Component | Proposed responsibility |
| --- | --- |
| `python/meshtrain/cuda_gradient.py` | `CudaGradientSynchronizer`: fixed CUDA parameter layout, gradient validation/packing, staged native SUM, explicit averaging and completed copy-back. |
| `training/workload.py`, `inputs.py` | Common saved CPU inputs and mathematical workload; additive device execution contract and schema dispatch; validate before moving anything to CUDA. |
| `training/worker.py` | Device-selected forward/backward/SGD, ordered gradient/loss collectives, diagnostics and completion artifacts. |
| `training/reference.py`, `verification.py`, `artifacts.py` | Ordinary device-selected combined-batch reference, versioned evidence, independent trajectory checks and recomputed GPU evaluation. |
| `training/__main__.py`, `launcher.py` | Explicit CLI selection, fresh processes, bounded worker supervision and original diagnostics. |
| `tools/check_cuda_trainer.py`, `tests/cuda_training/` | Installed-wheel hardware checks, outer process-group containment and focused boundary/failure fixtures. |

Keep device setup and metrics in a small focused training helper rather than expanding `worker.py` into a second runtime framework. Share small preparation/artifact/comparison helpers; keep reference arithmetic independent from the synchronizer and distributed step loop. Move existing completion-writing code into a neutral helper if needed to remove the reference's dependency on the worker module, retaining schema-1 output semantics.

No native core/binding algorithm change is planned. No CUDA work runs on root-package import or ordinary CPU training. CUDA imports/initialization and CUDA-specific controls occur only on the selected path. Keep existing CPU/build locks; reuse the separate CUDA lock rather than resolving another framework version.

## Prepared inputs and execution identity

CPU runs retain config/report schema 1, their exact default workload, `full_acceptance` meaning and accepted tolerance contract. Introduce schema 2 for CUDA configs/results; do not silently reinterpret a schema-1 CPU bundle as GPU training. Preparation still saves the CPU-created initialization, teacher-generated data and exact modulo-1024 schedule used by M1. GPU workers/reference load and validate these digests/layouts on CPU, then move their own model, features and labels to the explicit device. Initialization is not independently regenerated on GPU.

The immutable CUDA context includes the model/layout, input digests, world/step/local-batch sizes, SGD/loss/normalization settings, logical device, host-memory mode, Torch/NumPy versions, and requested precision/determinism policy. Hash it into the existing application fingerprint. Rank/endpoint/run-ID contracts are unchanged. Resolve and validate actual execution settings before native startup and before reference execution. Host-specific UUID/PID/free-memory observations belong to completion evidence, not a shared identity requiring different processes to have the same allocator state.

CUDA execution policy is explicit: eager FP32, no autocast or gradient scaler, one CPU intra/inter-op thread, deterministic algorithms with `warn_only=False`, cuDNN benchmarking disabled, and IEEE FP32 for global/CUDA-matmul/cuDNN precision using the new `fp32_precision` APIs. Do not mix these controls with legacy `allow_tf32` or other precision setters. Set `CUBLAS_WORKSPACE_CONFIG=:4096:8` before importing/initializing Torch in CUDA CLI processes; accept an already matching value and reject a conflicting one. Require `NVIDIA_TF32_OVERRIDE` and `TORCH_ALLOW_TF32_CUBLAS_OVERRIDE` to be unset or `0`; record their values and reject enabled/conflicting values. Inspect device/schema selection with the standard library before optional framework imports, including `worker` and `verify` commands. The reference uses the same policy. Read back effective precision/determinism settings, CUDA runtime/component versions, build configuration and relevant environment overrides. An unsupported deterministic operator is a failed check, not a reason to disable determinism without revising the design.

Preparation may inspect the installed runtime and construct CPU inputs; it does not need to allocate a model on the GPU. Worker/reference preflight must execute actual allocation, copy, MLP forward/backward and completion. A CUDA wheel name or driver banner alone does not prove supported kernels. Availability/runtime/device errors must be useful and must not fall back to CPU. Global settings are CLI-owned; constructing the library synchronizer must not reconfigure application-wide precision or threading.

## Gradient synchronization and training order

Proposed optional API: `CudaGradientSynchronizer(model, world_size, *, device, pin_memory=True, max_staging_bytes=268435456)` and `synchronize(communicator) -> CudaReductionTiming`. Keep the current CPU `GradientSynchronizer` API/behavior intact.

Capture sorted trainable parameter names, identities, shape/count/offset, dtype and indexed CUDA device. Reject empty/no-trainable models and mixed device/dtype/layout. Own an ordinary contiguous CUDA FP32 flat tensor of the total gradient count and a matching `CudaStagingAdapter`; allocate ordinary workspace even inside caller inference mode. Retain model/parameter/workspace owners and reject overlapping synchronizations with a nonblocking operation guard. The configured world size is the caller's native group world size; the trainer derives both from the same validated config.

Before any packing/native call, validate unchanged parameter identity/device/layout and all gradients: present, matching dense strided FP32 shape/device, finite, ordinary tensor without subclass, inference, forward/reverse AD or negative/conjugate view state. Reject capture before launching even validation kernels; use guarded forward-tangent inspection as in #10. Noncontiguous dense gradients may be explicitly packed; this is a documented device copy, never silent dtype/device coercion. Avoid rebinding `parameter.grad` storage.

On the configured device's current stream, pack detached gradients into the retained flat tensor, call `CudaStagingAdapter.all_reduce_sum_` exactly once, check the reduced tensor is finite, divide by world size, and copy slices back to the original gradient storages. Check the averaged values and complete the stream before returning, including copy-back. Return the primitive's immutable timing record, clearly labeled as its inner staged-SUM interval; it excludes packing/averaging/copy-back. The worker measures the complete synchronizer wall interval separately. Keep owners alive through the final wait. Producers/aliases must be ordered onto the selected stream; graph capture, unordered mutation and concurrent optimizer use are unsupported.

Each worker step uses this order:

1. Zero gradients; gather that rank's equal-sized minibatch on its GPU; compute mean cross-entropy and validate finite loss; run backward on the same ordered stream.
2. Require native sequence `2 * step`, then synchronize gradients. The native engine performs SUM; the Python gradient adapter performs the explicit division.
3. Copy detached local loss into a retained ordinary one-element CUDA FP32 buffer. Use a separate one-element staging adapter for loss SUM at sequence `2 * step + 1`; check finiteness, divide explicitly and complete the selected stream.
4. Snapshot global mean loss and averaged gradients, then apply the same SGD (`lr=0.05`, zero momentum/weight decay, `foreach=False`, `fused=False`). Complete the stream, reject nonfinite updated parameters and save that step's parameter snapshot. Successful completion reaches sequence `2 * steps`.

Only forward/backward generates autograd state. Communication sees ordinary detached fixed buffers after backward. The full-gradient and loss host buffers consume 2,708 requested bytes per MLP worker (676 FP32 gradient elements plus one FP32 loss); pinning is explicit and allocation failure cannot silently select pageable memory.

Local invalid inputs fail before native admission/copy-back. A reduced nonfinite gradient fails before averaging/copy-back/SGD. A native or CUDA failure propagates its original context, and the worker performs no further collective or SGD. A loss-stage failure can follow successful gradient copy-back; it still prevents that step's SGD. A later copy-back/optimizer failure may leave partial gradient/parameter changes: abort the group, never retry in place, and withhold successful completion. Preserve #10 poison/retained-owner/secondary-cleanup reporting. The gradient wrapper also owns failures in its added packing/check/averaging/copy-back phases: retain relevant parameters/gradients/workspaces, poison reuse, close native communication before attempting to settle the captured stream, and attach secondary cleanup diagnostics to the original error. Metadata rejection before work does not pretend that peers rolled back; the trainer aborts that job. Process termination does not prove recovery of a poisoned GPU; unknown cleanup remains failed/unknown.

## Independent GPU reference and numerical evidence

After all workers have exited/reaped, the verifier computes an ordinary GPU reference in its separate process relative to the workers. For `run`, the parent can perform this only after supervision finishes; independent deployments use the separate `verify` command. The reference starts from the saved CPU initialization moved to the same indexed GPU and uses each step's rank-ordered combined batch in one forward/backward/SGD. It does not instantiate a communicator/synchronizer or consume distributed losses, gradients or parameters to generate its expected trajectory.

Retain finite FP32 per-step losses/averaged gradients/post-SGD parameters, complete CPU-serialized final state, fixed-set evaluation before/after, source/input/run/context identities and native sequence. Compare every worker with the reference and every worker pair. Evaluate the existing elementwise rule in FP64: `abs(actual-reference) <= 1e-6 + 1e-5 * abs(reference)`. Report per-step maxima, failure counts and first offending flat index/parameter name; retain raw comparisons, not just a pass flag. This same rule covers final state and evaluation metrics. Recompute initial/final evaluation on GPU using the configured policy, and check final trace snapshots against saved state.

GPU arithmetic and different batch shapes can differ numerically despite deterministic settings. Keep tolerances unchanged and investigate divergence, precision, batch ordering or ReLU boundaries; do not use CPU evaluation as the GPU oracle or widen tolerances to produce acceptance. Identical deterministic settings are a controlled experiment, not a promise of cross-version/hardware bitwise equality.

Schema-2 completion manifests bind `trace.npz`, CPU `final.pt`, CUDA metrics and environment evidence with digests. Validate all required keys/shapes/types/finite values, config/mode/device/precision/sequence, input digests, runtime identity and rank ownership. Write `verification.json` with failed status before work so stale success cannot survive interruption. Missing completion, tampering, wrong metadata or a failed group must not become verified training. Traces/evidence are not checkpoints.

For CUDA reports use `profile=cuda_full` only for world two/100 steps/local eight with all comparisons passing and finite strictly decreased fixed-set evaluation loss for both workers and the reference. Expose a separate `cuda_training_acceptance` result and scope; keep CPU M1 `full_acceptance` false for GPU output. Smaller/custom CUDA runs can pass parity with `profile=cuda_smoke_or_custom` but cannot satisfy full CUDA acceptance. The issue's aggregate requires both pinned and pageable full profiles plus the focused checks; one passing report alone cannot close M2.

## Timings, memory and scope

Retain every rank/step's two `CudaReductionTiming` records tagged `gradient`/`loss`, native sequence, count, byte size and host-memory mode. Record complete gradient-sync wall time, instrumented completed step wall time and nested trace-copy time. Step time includes finite-value checks, staging, SGD, synchronization and diagnostic snapshots; report whole-run wall time separately. These are instrumented training observations, without a throughput or overlap target. Binding/native time combines Python/native entry, peer waits, TCP and CPU reduction; no wire-only/reduction-only decomposition is available from #10.

Mark the first five steps of each 100-step trajectory as timing warmup; retain them and all their numerical checks. The remaining 95 measured steps per rank/mode yield 380 measured rank-step records and 760 staged-call records across both full modes. Do not reset parameters after warmup or add hidden training updates. Summarize each operation's stages with per-rank medians/ranges and maximum-rank completion per matching step. Do not sum nested timers or medians as independent costs. Tiny smoke runs may have no post-warmup timing samples and cannot satisfy this timing count.

Record per-process allocator baseline and peaks for allocated/reserved device bytes, resetting peak statistics at a documented boundary before training and again separately for reference work. Record synchronized `mem_get_info` observations without treating them as an exclusive reservation. Record CPU RSS high-water mark with Linux units, requested pinned/pageable storage and explicit model/gradient/flat/loss/dataset bytes. In this MLP, parameters/gradients/flat/loss account for 8,116 device bytes and features/labels for 73,728, before activations, temporaries, index tensors, allocator rounding, cuBLAS workspace and context/driver memory. Requested pinned bytes are not actual locked-page/RSS cost; report that distinction. Do not sum per-process peaks as a measured simultaneous device peak.

Preflight both workers and compare UUIDs in the shared-GPU profile. Save `CUDA_VISIBLE_DEVICES`, physical identity/capability/total memory, architecture support, driver/runtime/component/build versions and installed extension/package paths. The small workload and sequential reference limit simultaneous residency; two processes sharing the GPU already worked in #10, but this is not proof that training fits. OOM/unavailable hardware is an explicit failed/unverified profile, not an automatic smaller replacement or skip. Do not evict unrelated jobs or reset/install the driver.

## Containment and focused verification

The proposed `tools/check_cuda_trainer.py --mode smoke|full --output DIR [--wheelhouse DIR]` builds an sdist-derived wheel, uses a fresh isolated runtime with the existing CUDA lock/hash checks and runs installed code outside the checkout with `-I`. Reuse focused setup/source/evidence helpers where practical; preserve `check_cuda_adapter.py` behavior. Use a disk-backed Linux output with at least 12 GiB free and setup temporary files on that filesystem. Reject nonempty output. Record behavioral source before/after, lock/wheel hashes, commands, logs and imported paths; the final source must match the tested implementation revision.

The Torch-free outer controller directly launches installed `prepare`, concurrent independent `worker` commands and then `verify`, keeping every training/reference process as its own direct child that it can wait/reap. Each child gets an owned process group; do not rely on killing a nested supervisor to reap grandchildren. Bound the whole profile to one 180-second execution deadline including preparation/worker startup, training, reference and verification, followed by at most five seconds for TERM and five for KILL/reaping, a 190-second acceptance bound. The worker phase has a 120-second cap within that total; native startup/collective deadlines remain 30 seconds. Record creation/ownership before processing deferred interruption, all PIDs/exits/reaping and primary versus secondary cleanup errors. GPU/library stalls outside the bound fail; no retries or deadline/tolerance changes to rescue a result.

The existing convenience `run` command still supervises its fresh workers with a 120-second default worker timeout and five-second termination grace. Its worker timeout does not cover reference/driver work in the parent. Document that boundary; the direct-child external runner provides complete acceptance containment. Check CUDA `run` dispatch in a focused smoke fixture as well, with cooperative signal handling and ownership records for nested workers; do not call a killed parent's orphaned children reaped by the outer controller. If containment cannot be established, mark cleanup unknown and fail that fixture.

Full local acceptance includes one-rank/three-step parity in both modes; two-rank/100-step parity in both modes; and a two-rank/three-step pinned run that executes forward/backward/synchronization/SGD on a nondefault stream with explicit producer dependencies. A private focused gradient fixture supplies distinct known gradients, checks exact averaging/noncontiguous packing/storage identity and rejects missing/wrong-device/dtype/layout/nonfinite/replaced parameters before native sequence change. Check post-return cross-stream consumption only after documented ordering, and concurrent-use rejection without disturbing the active call. Reuse #10's already established primitive contract cases where unchanged instead of duplicating its whole matrix.

A private two-worker fixture closes one real communicator after backward of step 1, before that step's gradient SUM. Log each actual SGD entry in both workers independently; require exactly one completed prior update, no step-1 update, no successful completion/verification marker, useful rank/native diagnostics and all owned PIDs reaped. GPU failure policy is inherited; do not corrupt the CUDA context to manufacture a hardware fault.

Focused verifier corruption cases alter copies of one successful tiny bundle: missing/invalid completion, digest mismatch, stale context, wrong device/precision/mode/sequence, and one beyond-tolerance or nonfinite gradient/parameter snapshot with manifest digests updated. Every case must replace any previous success with failure. Standard-library controller fixtures exercise timeout, a later spawn failure and interruption at child-registration boundaries without claiming GPU execution. Verify unavailable-CUDA rejection in the existing CPU-only runtime.

Regular CPU push/PR jobs and M1 nightly/manual coverage remain unchanged. Run affected short CPU trainer/binding regressions after shared Python changes, and record exact-revision CPU CI. One actual local GPU full check is required to close #11; do not defer it to an unavailable GPU nightly runner. Broad deployment/fault matrices remain nightly or later scoped work. GPU containers, Windows, physical hosts, distinct GPUs, baseline algorithms and efficient overlap have no evidence here.

## Rationale and alternatives

1. **Extend the trainer with explicit mode/schema dispatch (recommended).** Reuses exact saved inputs, the independent reference and one verifier, while a separate CUDA gradient wrapper preserves the CPU API. Requires targeted CPU regressions and strict artifact dispatch.
2. **Create a separate CUDA trainer package.** Isolates M1 source but duplicates preparation, schedule, supervision and corruption checks, inviting numerical/evidence drift as the project grows.
3. **Generalize into a backend/plugin training framework now.** Could serve future devices, hooks and optimizers, but adds unneeded interfaces before the second concrete path is verified. Keep small real seams and revisit with actual requirements.

The new schema, precision policy and acceptance labels warrant ADR 0005, accepted under the owner's conditional instruction after independent review; they add a GPU training contract without superseding the CPU history. Keep rationale here and ordinary implementation comments/docstrings at two physical lines or fewer.

## Risks and open choices

The technical defaults above were independently reviewed without findings and authorized by the owner's conditional go-ahead. Material risks are GPU batch-shape numerical drift, accidental CPU/schema regression, unaccounted framework/context memory and driver waits beyond native timeouts. Fixed tolerances, explicit schema dispatch, resource observations and independent process containment are the planned controls. Live evidence remains required.

## Primary references inspected on 2026-10-18

- [PyTorch 2.14 CUDA semantics](https://docs.pytorch.org/docs/2.14/notes/cuda.html): use the new precision controls consistently; backward/consumer streams require ordering; tensor allocation and allocator reservation measure different quantities.
- [Deterministic algorithms](https://docs.pytorch.org/docs/2.14/generated/torch.use_deterministic_algorithms.html) and [reproducibility](https://docs.pytorch.org/docs/2.14/notes/randomness.html): strict mode can reject unsupported operations and is not a cross-environment reproducibility guarantee.
- [Numerical accuracy](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html): mathematically equivalent batched and sliced operations may differ numerically.
- [NVIDIA cuBLAS reproducibility](https://docs.nvidia.com/cuda/cublas/index.html#results-reproducibility): explicit workspace configuration is one multi-stream determinism control and has memory cost. Record the actual locked component version instead of equating its version to the wheel's CUDA tag.
- [Torch 2.14.1 CUDA loss source](https://github.com/pytorch/pytorch/blob/v2.14.1/aten/src/ATen/native/cuda/Loss.cu) and [CrossEntropyLoss](https://docs.pytorch.org/docs/2.14/generated/torch.nn.CrossEntropyLoss.html) informed the planned mean-loss path. Source/documentation inspection does not prove the full GPU model executes under the requested policy; live forward/backward remains required.
