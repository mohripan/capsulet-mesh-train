# Design: M1 failure, clean-build and four-container validation

Read [proposal.md](proposal.md) for scope/authorization and [tasks.md](tasks.md) for progress. Preserve the [M1 contract](../../superpowers/specs/2026-10-16-cpu-mvp-design.md), [ADR 0001](../../adr/0001-blocking-centralized-fp32-communicator.md), [ADR 0002](../../adr/0002-python-buffer-ownership.md) and [ADR 0003](../../adr/0003-replicated-sgd-training-contract.md).

## Approach and affected boundaries

Extend validation around the implemented engine and installed trainer. The C++ core continues to own transport/reduction, optional bindings retain NumPy storage, and the existing Python worker performs explicit averaging/SGD. No public fault flags, protocol changes, DDP/MPI/NCCL delegation, recovery or remote scheduler are needed. Fix a demonstrated contract bug within scope if found; a materially different public contract requires revising the proposal and considering a new ADR before implementation.

Implemented areas:

| Area | Responsibility |
| --- | --- |
| `tests/` and `tests/CMakeLists.txt` | Linux native fault executable, private phase-control helpers, per-case CTest registration and evidence. |
| `Dockerfile` | TCP-off native validation stage and an installed CPU trainer validation image; preserve pinned bases and locks. |
| `tools/check_training_containers.py` | Standard-library Linux/WSL host controller using the Docker CLI; no host Torch dependency. |
| `tools/check_m1.py` | Fresh-output orchestration, bounded commands, component result manifest and evidence collection. |
| `tests/validation/` | Real controller setup/worker/interruption and ownership checks. |
| `.github/workflows/` | Explicit nightly/manual M1 lane; keep existing push/PR native/binding/trainer regressions. |
| `docs/validation/`, development/training/navigation docs | Reproduction, raw results, limits and M1 closure when earned. |

These entry points reuse `check_python_bindings.py`, `check_trainer.py`, native numerical/protocol tests and installed-consumer checks. The permanent installed runtime uses a separate packaging helper; existing binding, trainer and core implementations are unchanged. New ordinary code comments/docstrings remain at most two physical lines; rationale belongs here.

## Native fault matrix and phase evidence

Use actual Linux child processes, the real TCP adapter and communicator. Three ranks per case provide a root, a nonroot target and another surviving worker. Both startup and collective timeouts are explicitly 1000 ms. Test-only control pipes carry phase/release messages, never tensor data. The controller tracks ownership before spawning and drains every output stream without blocking on a full pipe.

| Phase | Target/action | Positive staging evidence |
| --- | --- | --- |
| Startup | Rank 0, SIGKILL / SIGSTOP | Real listening socket has been created inside `connect_tcp`, before membership can complete. |
| Startup | Rank 1, SIGKILL / SIGSTOP | Connection to the real root exists; the first HELLO send is held inside the startup path, so root cannot release the group. |
| Active collective | Rank 0, SIGKILL / SIGSTOP | Communicator has admitted sequence 0 and entered a real transport receive; at least one contribution is held by the test fixture. |
| Active collective | Rank 1, SIGKILL / SIGSTOP | Sequence 0 is admitted, but this rank's contribution is held before sending; root is awaiting the missing contribution. |

Startup observation uses narrowly scoped executable-local linker wrappers for the actual `listen`/first `send`, following the existing resolver-test pattern. Successful OS calls retain real behavior; the wrappers only signal/gate the selected phase. Collective observation uses a private `ByteTransport` decorator, as the existing close test does. It delegates to the real joined transport with the **original absolute deadline**. No test wrapper is linked into the library, wheel or ordinary trainer. No public socket handle or test control crosses the engine API.

Launch/control ordering ensures incomplete membership or an unsent contribution persists until the signal is confirmed. For SIGSTOP, verify the owned child really stopped while its socket remains open; do not replace the stall with a disconnect or release it before survivor deadlines fire. For SIGKILL, inspect the actual signaled wait status. Release only healthy fixture gates after the target action. Any gate wait is bounded and counts inside operation/case elapsed time; readiness is not a reason to reset a timer. Failure to reach the intended phase is a failed case, not a skipped test or an injected failure at another phase.

The fixture worker emits structured native error context and exits nonzero on the expected engine failure. Surviving startup ranks must not obtain a ready group. Surviving collective ranks must fail, keep sequence 0, enter `failed`, reject another collective and support idempotent close. Because the held contribution prevents a result, this scenario does not depend on an all-rank success transaction that ADR 0001 does not promise. Killed/stopped targets cannot emit normal engine diagnostics; report their action/PID/wait status rather than fabricating one. Peer identity/sequence is required only where available (e.g. pre-HELLO startup may not know the peer).

Accept bounded `peer_closed`, `timeout`, or the documented startup transport failure appropriate to the action/phase; require the planned category set and real phase/endpoint/rank/run context, not a single guessed causal ordering. A pure stall must demonstrate at least one survivor's timeout while the victim stays stopped. The controller may force-kill the intentionally stopped target only after survivor evidence or when the case has already failed. Killing healthy workers as fallback cleanup cannot count as native failure detection.

## Timing, watchdogs and resource checks

Each named case starts its monotonic timer immediately before the first worker spawn, then includes all spawning, phase synchronization, fault injection, survivor failures, target termination, wait/reaping and resource assertions. Require completion strictly within five seconds; native operations retain one-second deadlines. A controller cutoff before five seconds reserves time for cleanup; no successful result is emitted until cleanup is complete.

Register each of the eight standalone cases separately with CTest label `m1_integration` and an independent five-second test timeout. CTest timeout is a **failure**, not an acceptable way to satisfy native cancellation or cleanup. The outer Docker controller has a separate bounded container watchdog and removes the owned case container/tree if an inner watchdog fires. A killed fixture cannot certify its children were reaped; record failed/unknown cleanup and fail validation. The five-second bound applies to the already-built native process scenario, not image build/pull, framework imports or Docker daemon response. Do not relabel Docker management time as native communication latency.

Every healthy worker takes an in-process descriptor baseline before `connect_tcp`, after establishing the fixture's stable control/logging descriptors. After the native error is recorded and failed construction or communicator/transport objects have been destroyed, measure/assert baseline restoration **while that worker is still alive**, before sending its final cleanup record and exiting. Keep the fixture descriptor set identical at both measurements. Record rank, phase, before/after counts and cleanup status; missing records or fixture assertion failures cannot be accepted as an expected nonzero engine exit. This catches native error-path leaks that process exit would otherwise conceal. Killed/stopped victims receive a separately labeled OS-reclamation/wait-status check, never a claim that their destructors ran.

The controller separately requires all owned child PIDs reaped, its own descriptor baseline restored and the root endpoint immediately reusable with the engine's normal socket options. TIME_WAIT is not a leaked listening socket. Reuse a long-lived controller to run 20 additional fresh failed groups across all eight cases (round-robin), retaining both worker and controller evidence. A separate watchdog process receives BEGIN/END messages around each complete group and enforces five seconds per iteration, including cleanup; BEGIN precedes first worker spawn and END follows all assertions. A watchdog expiry fails/terminates the batch rather than continuing with uncertain ownership. The repeat-batch CTest timeout is a separate 110-second containment bound, not a five-second timeout for all 20 groups and not a substitute for per-group enforcement. Reset run IDs and ports per attempt; successful cleanup is required before a subsequent attempt. Repeats detect leaks; they do not retry failures until green.

Existing 1–5-worker/count/fragmentation/metadata/slow-progress/lifetime suites remain required inputs to the clean validation. New coverage supplements their self-termination/raw-peer cases with externally signaled owned processes and explicit startup phase proof.

## Installed image and four-container data flow

Add a `trainer-container` validation target based on the existing pinned CPU toolchain/wheel cache. Build an sdist and its wheel, hash-check/install locked CPU dependencies and install the wheel in a stable private environment (planned `/opt/meshtrain`). Use that interpreter with `-I`; assert imported package/extension paths are inside the installed environment and report wheel/lock hashes and versions. This is a validation image and may retain build tools/source; optimizing a production runtime image is outside scope. No dependency upgrades are planned.

The host controller accepts `--image IMAGE --mode smoke|full --output DIR`. Resolve the tag once to an immutable local image ID and use that ID for all helper/worker containers. Refuse a nonempty evidence directory. Use argument lists, no shell-built commands, a fresh UUID owner label and unique container/network names. Register intended resource names before invoking Docker so a partial create/start failure still has cleanup ownership. Never use daemon-wide pruning or a broad name-prefix deletion.

1. Prepare the immutable input/config bundle once in a temporary helper container using the installed `prepare` command. Pass four ordered aliases (`worker-0` through `worker-3`), explicit port 29500, wildcard listening and a fresh run ID. The smoke profile is four ranks/three steps/local eight; full is four ranks/100 steps/local eight. Keep the M1 model, seeds, normalization, optimizer and one-thread execution unchanged.
2. Create a private user-defined bridge network, without host networking or published ports. Create four worker containers with distinct aliases and independent writable root filesystems; no shared run/output volume, host PID namespace or Docker socket is mounted into workers. Copy the same config/inputs to each **before** launch. Workers recompute their input/fingerprint checks as usual. Each container runs the installed per-rank worker as its main process using exec-form arguments, with no nested local launcher.
3. Start all ranks and monitor their states together. Do not block waiting for rank 0 before checking peers. Save every exit code, rank-tagged stdout/stderr and selected inspect metadata; bound Docker CLI calls and write logs directly to files to avoid full-pipe deadlock. First observed useful failure is primary; later exits/forced cleanup are secondary, without claiming causal ordering.
4. After all ranks exit zero, copy only each rank's expected output directory into the controller evidence bundle. Do not read worker artifacts as a live synchronization path. Create a separate verifier helper from the same image ID with networking disabled; copy config/inputs and all rank outputs, run the existing `verify` command, and collect its reference/report. It computes an ordinary combined-batch trajectory after workers have stopped.
5. Require all native/Python artifact checks, full final-state keys, every rank/reference/pair comparison, finite lower full-profile evaluation loss and expected sequence. Only full mode can set full trainer acceptance. Four-container smoke is labeled separately; an aggregate controller status cannot succeed with missing ranks, nonzero exits, mismatched image/input identity or failed cleanup.
6. Preserve evidence, then remove every helper/worker container and the private network owned by this UUID. Inspect/list owned resources to confirm removal, and record the outcome. Failure, timeout, exception, partial startup and SIGINT/SIGTERM all follow the same cleanup path. If Docker is unreachable, report cleanup unknown/failed and return nonzero rather than asserting that resources disappeared.

Default healthy worker-group deadline is 120 seconds from first worker start through all worker exits, including framework import. Each short Docker control command is bounded by at most five seconds and the remaining phase budget. Preparation, successful artifact collection and offline reference verification each have a separate 120-second budget. On failure/interruption, one 15-second cleanup budget includes stopping/force-killing owned containers, best-effort diagnostics and removing/checking the entire owned resource set; stop/kill resources collectively and reserve removal time instead of accumulating Docker's default per-container stop grace. Incomplete required evidence or cleanup fails validation. Build commands have separate recorded limits. These Docker budgets are distinct from the controlled native five-second failure test; exhausted budgets fail validation and do not permit silent retries.

## Controller negatives and evidence ownership

Use actual Docker resources for focused negative checks: a bad per-rank configuration path while another worker is running, external SIGKILL of an owned running worker, a later create/start exception, and interruption after resources exist. Private test observers may coordinate the validation controller; no fault knob is added to the production trainer. Container lifecycle tests do not claim precise native phase timing; that proof belongs to the native matrix. In each negative, require a failed group, useful rank/action diagnostics, no successful overall report and removal of all owned resources.

Create a uniquely named sentinel container/network outside the run's owner label and leave them intact through these checks, then remove the sentinel through its separate test owner. Run the successful four-container smoke twice with fresh attempts to check cleanup and alias reuse, then the full profile once. An intentionally corrupted collected artifact (using refreshed file metadata as necessary) must still fail existing numerical/identity verification; preserve the original full-run bundle separately.

Use versioned `validation.json` with source revision/dirty flag and relevant source/lock/wheel/image digests, command/phase statuses, native case timing/categories/PIDs/reaping/resource results, Docker resource IDs and cleanup, numerical report location and overall status. Begin with an unsuccessful/in-progress status and publish success only after all required checks and cleanup pass. A numerical subreport may pass while controller cleanup fails; the aggregate must remain failed. Capture logs on failures as well as successes. Record installed runtime paths, compiler/CMake/Python/Torch/NumPy versions and OS/container engine/kernel. Do not label an uncommitted source build as an exact clean commit.

Retain config, input bundles, traces, final states, full numeric reports, logs and manifests under ignored `build/m1-validation/`-style output. Commit a concise human report and raw timing/error CSV/JSON with content hashes under `docs/validation/`; stable raw evidence uses LF attributes as in #7. CI uploads selected evidence (including failure/cleanup logs) rather than entire virtual environments, package caches or Docker layers. Missing required evidence fails the run, not merely the documentation step.

## Clean orchestration, CI and completion

The host runner requires Linux/WSL, CPython 3.12 or newer, a Docker CLI connected to a Linux daemon, and the repository checkout. It uses only the standard library: no host venv, build packages, NumPy or Torch is required. Preflight reports Python/daemon versions and fails clearly for missing prerequisites; installation of Docker itself is a documented environment prerequisite. Planned primary command:

`python3 tools/check_m1.py --no-cache --output build/m1-validation`

The standard-library host runner builds/runs the native TCP-on target, a new TCP-off native/consumer target, Torch-free installed binding target, short installed trainer target and the installed validation image. It then runs the new native fault cases/repeats, existing native container checks, a clean localhost four-process/100-step installed-wheel comparison, and the container smoke/full/negative checks. The localhost comparison executes `check_trainer.py --mode full` **inside an owned pinned validation-image container**, where Linux CPython 3.12 and locked build packages already exist; that tool builds/installs its fresh wheel/runtime there. It is labeled four processes in one container, distinct from the subsequent four-worker-container deployment. Copy out its evidence after it stops. Reuse one built image per target and existing tools; do not depend on development wheels, host Torch, old output files or a mounted build directory. Fresh CI runners use the same host preflight/command and Docker stages, without a hidden toolchain-venv bootstrap.

`--no-cache` bypasses Docker build-layer reuse for the acceptance run. Dependency wheel/download caches may remain, but hashes are required and all CMake output, sdists/wheels, runtime environments and run artifacts are freshly produced. Base digests/direct versions follow the current repository pins; apt transitive packages follow Debian repositories, so this is reproducible procedure/evidence rather than a promise of bit-identical hermetic rebuilds. Record cache mode and actual versions. Source changes invalidate the current run's claimed revision and require affected validation again.

Add a separate GitHub workflow for nightly (proposed `23 18 * * *`, UTC) and `workflow_dispatch`, running the full command on Ubuntu 24.04 with explicit job timeout, read-only repository permissions and verified full-commit action pins. Always attempt bounded cleanup/evidence collection and upload artifacts even when a check fails. Scheduled runs use the default branch and may be delayed by GitHub; a manually dispatched exact-revision pass is required before closure. New broad CTest cases carry `m1_integration`; the push/PR native Docker invocation excludes that new label while retaining all seven existing native entries and its existing container scripts. Current binding and short trainer push/PR jobs remain. Moving existing broad tests or adding unrelated CI policy is excluded.

At implementation acceptance, run one complete fresh-directory/no-layer-cache pass locally and one exact-revision manual CI validation, including the four-container full workload. Do not wait for a future nightly run or close from configuration alone. Read back #3–#8 evidence/status before closing #8/#2 and M1; retain unrelated local files, commit/push to main without co-authors and update navigation to M2's first unmet issue. Actual results are recorded in [verification.md](verification.md).

## Implementation details and review

`failure_control.hpp` owns fixture descriptors and the persistent watchdog; `failure_tests.cpp` owns child processes, staging, bounded collection and resource assertions; `failure_worker.cpp` isolates executable-local socket wrappers and the real transport decorator. Child ownership is assigned only after successful `posix_spawn`, so a failed spawn cannot expose an unspecified PID to cleanup. Surviving workers remain alive for a controller acknowledgment after their post-destruction descriptor report. `/proc` observation separately proves that a stopped target retains its actual sockets.

`validation_support.py` owns bounded Docker commands and UUID-scoped resources. Cleanup uses one 15-second budget, reserves time for removal, appends command/history evidence during recovery and retains the original failed result. The controller resolves its image once and uses that immutable ID. Legacy native shell checks accept the same owner label, allowing the orchestrator to verify their cleanup even after a failed shell trap. No daemon-wide deletion is used.

`check_m1.py` records behavioral source hashes before work and verifies them afterwards. Documentation edits do not invalidate a running check; changes to implementation, tests, build inputs or workflows do. The validation image intentionally retains source/toolchain files, while worker imports use the isolated installed interpreter. Docker build-layer reuse is disabled for acceptance; hash-checked download cache reuse is explicit.

## Alternatives, risks and ADR disposition

- Reuse existing native shell scripts alone: smaller, but their sequential waits and native-only workloads do not prove trainer/controller behavior or the new failure timing matrix. Reuse them for existing coverage, add a focused controller for the trainer.
- Docker Compose: convenient declarations, but adds a versioned tool and still needs explicit all-rank status, artifacts, deadlines and cleanup. Standard-library orchestration over the installed Docker CLI keeps this validation task's dependency surface smaller.
- Public engine/trainer fault hooks: simpler to trigger but alter production contracts for test coordination. Executable-local wrappers/decorators preserve the current boundaries; inability to prove a phase is a test failure.

Main risks are phase races, cleanup masking primary errors, Docker daemon slowness, stale artifacts, and slow dependency/framework setup. Address them through positive phase evidence, separate timing domains, immutable identities, fresh outputs, fail-closed aggregation and preserved raw results. CPU/container evidence does not establish GPU or physical-host scaling. Accepted ADRs already cover failure, borrowing and training evidence; no new ADR is warranted unless implementation exposes a lasting production decision.

- [GitHub scheduled events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) and [workflow artifacts](https://docs.github.com/en/actions/tutorials/store-and-share-data): manual acceptance and retained evidence alongside nightly automation. Documentation research is not runtime proof.
